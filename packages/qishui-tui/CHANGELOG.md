# Changelog

本包（`qishui-tui`）的变更记录，最新在上。

## Unreleased

### Added

- **用户主页（压栈页 `kind:'user'`）**：`screens/User.tsx` —— 昵称 / 抖音号 / 签名 / 统计（关注·粉丝·获赞·作品）+ 条目式入口：TA 的公开歌单、TA 关注的人、TA 的粉丝、关注 TA、取消关注 TA、拉黑 TA（过确认框）。与 CLI 的 `qishui user <id>` 同一份数据（`core.social.user`）
  - **关注态不猜**：`GetUserInfo` 回的 `UserData` 里没有「我关注了没有」这类水印，core 的 `User` 实体也就没有 `following` —— 所以这一页既不写「已关注」也不写「未关注」，「关注」与「取消关注」各成一条，点哪条就是哪个意图（`rowActions` 里艺人行的水印口径照旧，两处不混）
  - **风控**：`GetUserInfo` / `GetFollowingList` / `GetFollowerList` 实测连打两次就撞验证码（core 已按 5 分钟缓存兜住），所以这一页不做「进页就预取粉丝列表」，翻页只在人真的按下时发生
  - **入口**：搜索结果的用户行菜单里「打开 TA 的主页」（排在「打开 TA 的歌单」前面）、评论弹层里 `Enter` 看这条评论的作者；关注/粉丝列表里的人也是用户行，可以一路点下去
  - **列表源**：`ListSource` 新增 `user-following` / `user-followers`（渲染 `userRow`，游标用上游 `next_cursor`），`useList.ts` 导出 `userRow`
  - 条目构造抽成导出的纯函数 `buildUserSections`，新增 `test/user.test.ts` 三条离线单测（条目顺序、关注态不写结论、拉黑先过确认框、未登录置灰 + 「去登录」）
- **`ui/keys.ts` 的 `useKeys`：一次 read 带回多个字符时按字符拆开派发**：ink 的 `useInput` 把整串交给 handler，人快手连按 `jj` / `gG`、或一次粘贴多个字符时拿到的是 `'jj'`，而命令 handler 比的都是 `input === 'j'` —— 现象就是「按了两下、列表没动」（单测里 `printf 'jj'` 一个 chunk 灌进去也能复现）。现在命令类 handler（`App` 全局键、`useCursor`、侧边栏、搜索页的结果导航、正在播放、确认框、登录页）统一走 `useKeys`：多字符可打印输入按字符逐个派发；**鼠标报文与它的碎片**（`[<64;10;5M` / `10;5M`）、**带 ESC 的序列**、**带修饰键的**一律不拆（拆了会把 `<` `;` `M` 当成人敲的键，`<` 还是「后退 10 秒」）。文本输入处（搜索框、评论、歌单名/改名）继续用 `useInput`，它们本来就按字符收下。新增 `test/keys.test.ts` 四条纯函数单测

### Changed

- **「我的」页的散键收进操作菜单：`l` / `x` / `e` / `D` 四个键删除**
  - **账号行 `Enter` = 账号操作菜单**：扫码登录（换号 / 补登）、退出当前账号（只清本机 cookie）、刷新资料·会员·歌单、数据目录（只读）。未登录时这一行写「Enter 扫码登录（汽水音乐 App）」，登录入口不再靠记一个 `l`
  - **我的歌单每行 `Enter` = 行操作菜单**，复用列表页同一套 `buildRowActions`：打开歌单 / 播放整张 / 收藏这张歌单 / 改名 / 删歌单（删单仍过确认框）。为此给 `buildRowActions` 加了 `owned` 选项——`GetMyPlaylists` 不保证回 `owner.id`，拿它当唯一判据会让自己的歌单「不能改名、不能删」；「我喜欢的音乐」是自动歌单，归属确证也不给删。改名/删除成功后顺带 `afterWrite()`，本页歌单列表跟着重读
  - **页面级只留 `N`（新建歌单）与 `R`（刷新）**，两个都不会和别处撞；歌单区末尾另给一条「新建歌单…」条目，鼠标用户不必记键
  - 提示行与 `?` 帮助同步：`Enter 打开 / 操作菜单`；帮助里补「我的页：账号行 Enter = 登录/换号/退出」「我的歌单：每行 Enter = 打开/播放整张/收藏/改名/删除」

### Fixed


- **搜索页「查看全部 →」直接 404**：这一项以前把 `group.type`（上游 `display_type`）当 `search_type` 塞进列表页路由，而实测 `Search` 每个分组的 `display_type` 都是**空串** —— 请求打到 `/luna/search/` 就是 `Search HTTP 404`，页面显示「搜索 HTTP 404」的错误态。现在改成
  - **类型从 core 的派生字段拿**：`source.type` 用 `group.searchType`（core 按 `group.id` 的实测形态 `tracks`/`albums`/`artists`/`playlists` 映射），`ListSource` 的 search 分支也从 `string` 收紧成 `SearchType`，`useList.ts` 里那处 `as never` 一并去掉 —— 以后想再塞错类型编译期就红
  - **要不要给「查看全部」听上游的**：只有 `group.viewAll`（上游 `display_view_all`）为真才列这一项，「你可能想搜」这类聚合组（`top_results`，上游给 `false` 且没有单一类型）不再凭空给一个点进去就空的入口
  - **顺手**：分组标题的兜底从 `group.title ?? group.type ?? '结果'` 改成 `group.title ?? '结果'` —— `display_type` 是空串而不是 undefined，旧写法会让「歌曲」这类没标题的分组头变成空白
  - 真跑验证（一次上游读）：`周杰伦` 的 `all` 结果里四个分组各自 `searchType` 都对上，逐个请求 `/luna/search/{playlist,artist,track,album}` 都回 1 组 20 行；`top_results` 不给这一项
- **鼠标点歌曲：菜单不出来 / 闪一下**（收口后引入，两处叠加）
  - **建菜单不再等收藏状态**：`ui/rowActions.ts` 原先 `await core.library.isLiked()` 才摆条目，而 `isLiked` 的实现是**把整张「我喜欢的音乐」翻完**（找 liked 歌单 + 分页拉全部曲目，好几轮请求），只有 5 分钟账号缓存兜住第二次。现象：第一次点没画面，用户再点一下，先前排队的那次才把菜单打开——看着就是「弹层闪一下」。现在 `buildRowActions` 是**同步**的，状态只白拿 `core.cache.peek('liked-tracks','list')`（内存里有就说 已喜欢/未喜欢，没有就不写状态），真状态留到执行「我的喜欢」那一刻再读（单测断言建菜单期间 `isLiked` 一次都没被调用）
  - **列表页单击直达**：原来「点未选中的行只挪游标、点在已选中的行才开菜单」，单击歌曲等于什么都没发生。现在点一行就是开这一行的操作菜单（与 `SectionView` 的单击直达同口径）；防误触靠「菜单里还要再选一次」，删歌单另过确认框
  - **点击穿透这道闸**：弹层画在指针正下方，双击的第二下会打在菜单条目上直接执行。`SectionView` 挂载后 350ms 内的点击只挪游标、不跑 `onEnter`；键盘 `Enter Enter` 不受影响
  - **`useInput` 收到的鼠标报文实测**：一次点击派发 `[<0;x;yM` 与 `[<0;x;ym` 两次按键（开头的 ESC 被 ink 剥掉），被拆碎的半截报文也会单独进来，全部由 `isMouseInput()`/`stripMouse()` 挡掉；单独的 ESC 才带 `key.escape`——弹层的「Esc 关闭」没有被点击误触发，这次的现象与它无关

### Changed

- **「电台」改成「听歌」：从假列表页改成听歌模式单选台**：侧边栏第 3 项接的是上游**听歌模式**，不是电台——`FeedSongTab`/`FeedRadioTracks` 每次只随机回一小批（实测 6 首），是「随机播放的批次来源」。旧页面用 `useList` 硬凑 `count: 30` 当一屏列表、`hasMore:false`，那是假象：看着能浏览，其实每进一次都是另一批随机结果。现在这一页只回答「当前用哪个模式听」
  - **选中即切模式并起播**：常用三档（推荐/熟悉/新鲜，`FEED_PREFERENCE_MODES` 是 core 常量，骨架模式也画得出来）在页内直接选，45 个场景收进弹层（复用 `ActionMenuOverlay`，自带按游标滚动）；**只能有一个当前值**，`(x)` 标本机记住的 `config.feedMode`，`（上游当前）`标上游 `feed_mode_bar` 那一条，两者不一致就并存显示（不拿上游那一条当真相源）
  - **一批播完自动续一批**：新增 `src/feedStream.ts`（`FeedStream` + `FEED_REFILL_AT=2`），只在「剩 ≤2 首」时异步补一批接到队尾，队列空了整队换一批。止损是硬的：在途互斥、换模式/停流用序号作废慢回来的那批、连续 2 批取不到或某批回空就停流并给一句 error toast，**不留重试定时器**。续播的触发点算在 `p.on('queue')` 而不是 `ended`——core 到曲总是先发 `ended` 再动队列，在 `ended` 里同步数「还剩几首」数的是上一首那一刻的数
  - **谁该关掉无限续播**：`playTracks`（所有「用户明确点了某内容」的唯一漏斗）入口无条件 `stream.stop()`；空格/`n`/`p`/`s`/`r` 都不关流，`repeat:one` 天然不续。「停止自动续播」不另加散键，做成页内一条条目
  - **模式持久化**：core config 新增 `feedMode`（文法 `preference:<mode>` / `scene:<radioId>`，空串=没选过），解析/格式化用 core 导出的 `parseFeedMode`/`formatFeedMode`，不靠「纯数字就当场景 id」这种隐式判定。设置页 `feedMode` 只读（45 个场景没法 `Enter` 循环），值显示成人看的名字
  - **删掉的入口**：`src/screens/Radios.tsx`、`ListSource` 的 `radio:<id>` 与 `feed:<mode>` 两支（连带那个 `count: 30`）。发现页的「随便听听」改成进「听歌」页选模式，首页 `discover_radio` 块改成「点一下 = 把它设为当前模式并起播」（雪花 id 不在 45 场景里，就照实显示 `场景 <id>`，不假装认得）；`?` 帮助与提示行、侧边栏注释、路由分派一起跟上
  - 测试：新增 `test/feedStream.test.ts`（10 条，全注入假 deps——阈值才补、并发挡住、停流后在途不落队列、失败到上限只两句错且之后不再取数）、`test/listen.test.ts`（9 条，验 `buildListenSections` 纯函数：`(x)` 只标本机当前且整页唯一、`（上游当前）`可与它并存、场景弹层「先关再切」的顺序、缺 `radioId` 的进不了弹层、没数据时场景档置灰）；`test/tui.test.ts` 里原先借「电台」的五条按文字改指「听歌」，其中骨架那条从「无行可开」改成「有模式条目、按 `Enter` 只提示不起播」（常用三档不依赖请求，骨架也画得出来）
  - 口径来源：`docs/APP_ENDPOINTS.md` 对 `FeedSongTab`/`FeedRadioTracks` 的实测都是 `items[6]`
- **界面改成「只用 ASCII + 汉字」，播放条随之按宽度收起**：`▶⏸ ↻ ⇉ 🔊 🔍 ✕ ▍ ● ○ ♥ ★ ✓ ⠋ ▸ ◌` 这类图形/表情符号从界面上全清了（进度条 `━●─` 例外保留）。动机不是审美——同一码位在 emoji 呈现/中文字体下常占 2 格，`displayWidth()` 估不准，播放条与列表列会跟着错位。
  - **词表与标签收进两处**：`ui/theme.ts` 定 `SELECT_PREFIX`/`CURRENT_PREFIX`（都是 `>`）、`ERROR_PREFIX`（`x`）、`NO_TRACK_TEXT`；新增 `ui/playMode.ts` 出中文标签 `播放/暂停/载入/待播/出错`、`循环:关|全|单`、`随机:开|关`、`音量:60|静音`，播放条与「正在播放」共用一份口径。加载转圈 `⠋⠙…` 换成 ASCII `| / - \`。

  - 行对象复用 `ui/useList.ts` 的 `trackRow`/`playlistRow`/`albumRow`/`artistRow`（这四个从私有改成导出，字段映射只此一处），曲目还把**本组曲目**当 `list` 传进去，菜单里「播放这首」因此带「本页 N 首一起进队列」

  - 真跑验证：`周杰伦` 的歌曲组首行 `Enter` 出「播放这首 / 下一首播放 / 加入队尾 / 我的喜欢（切换）/ 评论 / 详情 …」，播放条没有出声；歌单组首行出「打开歌单 / 播放整张 / 收藏这张歌单」

  - **防抖 250ms**：手停下来才问一次，敲字过程中不请求上游；粘贴/快打一次 read 带回多个字符也只算一轮。在途请求带序号，回来的比当前这轮旧就丢掉（不然慢的旧结果会盖上新的）
  - **选中只回填，不重新联想**：`↑↓` 在面板里走高亮，`Enter` 或点一条把那个词送回输入框——面板原样留着、不再打上游。只有键盘在输入框里动了字才重新联想（同一词条也不重复问；问失败不记账，下次同样的输入还会再问一遍）
  - 词条右侧标出 `Sug` 的 `content_type`（歌曲/歌手/歌单…，实测就这几类）；面板占的行数从结果区可视高度里扣掉，不会把画面顶出终端
  - core 的 `recommendWords()` 与 CLI 的 `qishui words` 不动——这里只是 TUI 不再用它
  - 真跑验证（PTY 注键，`Sug` 共 4 次读）：打「周」1 次请求、「周」→挑「周杰伦」→再打「的」= 2 次（挑那一下不产生请求），联想中…只出现一次，输入行从 `周` 变成 `周杰伦`

### Fixed

- **登录成功后登录态不刷新**：三处叠在一起——① 弹层原来自己轮 `status()`，看到 confirmed 后再补一次 `qr.wait()`「让它走完入库」，而入库只发生在 `wait()` 里、`wait()` 又重问一次上游，二维码在登录完成后常被上游判成 expired/unknown，于是谁也没入库（toast 报「登录成功」，顶栏/侧边栏/账号页照旧未登录）；现在入库由 core 在观测到 confirmed 的那次 `status()` 里做完，弹层不再多问一次（详见 core 同条）。② 登录态改成**事件驱动**：`core/context.tsx` 订阅 `account-changed`，登录/切号/登出/`me()` 事后补全身份都会顶起 `sessionRevision` 让界面重读，不再依赖某个入口自己记得 `bump()`。③ 列表页 `useList` 的重取依赖里没有号（只认 `source`），匿名时打开的「随便听听/榜单」登录后仍是匿名内容——`activeUid` 现在进了依赖。附带：`membership:`/`library:` 的取数 key 补上登录与否（`GetMyInfo` 失败、uid 一直 undefined 时也能触发重取），顶栏/侧边栏/账号页在身份未知时显示「已登录（身份未知）」而不是 `undefined`。④ 出错不再只当「网络抖一下」：轮询/入库一抛就显式打出「登录流程出错（仍在重试）：<原因>」——以前入库失败会被静默吞掉，界面看着像还在等扫码，其实是永远不会成功
- **登录流程的出错不再被当成「网络抖一下」吞掉**：轮询/入库一旦抛错，弹层显式打出「登录流程出错（仍在重试）：<原因>」并继续轮（core 会自己补做入库）。原来一律静默记进 `error` 又不显示来源，入库真失败时界面看着像「还在等扫码」，是「扫成功了却什么都没落盘」最难查的那一段
- **按键冲突（ink 的 `useInput` 把每次按键发给所有活跃 handler，没有消费语义）**：账号入口只看 `0`（原先 `0`/`L` 双入口——`L` 同时被列表页当「加载更多」，两处会一起触发）；新建歌单用 `N`（`n` 是全局「下一首」）
- **帮助弹层在小终端上被裁掉顶部**：弹层内容是居中排的，超过终端行数时 yoga 会把上下一起截掉（`导航` 分组整段看不见）。现在正文走滚窗，任何行数都看得全
- **`process.exit` 时残留 mpv**：播放中直接退出（`q`/Ctrl+C）会留下跑到曲末的 mpv 子进程（实测干扰到 CLI 的「无残留进程」断言）；现在退出钩子兜底收掉
- **频繁切歌会同时响多个 mpv**：`AudioSink.start()` 原来先 `await this.stop()` 再起新的，快速连按切换时两次 start 会交错（旧的还没收完新的已起），同时留下多个 mpv 一起出声。现在 start 第一件事是**同步** `terminate()` 上一首（SIGKILL + 清 socket）再起新的，IPC 连接回来时用 generation 校验防止把旧 socket 挂到新进程上；实测并发 10 次 start 后只剩 1 个 mpv，stop 后归 0
- **播放进度/歌词跟着整曲时长走（试听片段下全错）**：分享页给的是试听片段（`演员` 整曲 4:21、实际只 0:52，且从 208.9s 起），原来进度条按整曲元数据画、歌词从 0s 对，播几秒就不同步。现在订阅 core `source` 后开 IPC 每 400ms 读 mpv 的 `duration`/`time-pos`：真实时长喂回 `player.setDuration()`、真实位置纠偏 core 时钟，曲终由 mpv EOF 或时钟先到推进（`repeat` 模式仍由 core 处理）；歌词按片段起点偏移

- **resize 时闪一下**：一帧全屏内容改动就是 `clearTerminal` + 重画一次，而一次 SIGWINCH 原来要画两帧——ink 自己那帧还按旧行数排版，我们 setState 触发的第二帧才纠正（PTY 实测相差 4～13ms）。现在宽度走 `width="100%"`（ink 自己就重算对），高度由 `useFullscreenRows()` 用 `prependListener` 抢在 ink 的 `resized()` 之前把新行数写进 yoga，**一次 resize 只剩一帧**（全屏重绘次数实测 2 → 1）
- **resize 把用户的滚动历史抹掉**：`cli.tsx` 现在在 TTY 里先切备用屏（`?1049h`），退出时 `?1049l` 还原；ink 满屏帧的 `clearTerminal` 带 `3J`（清回滚），留在主屏打就会连带清掉用户自己的历史。非 TTY 不切
- **resize 后布局错乱**：`width={stdout.columns}` / `height={stdout.rows}` 是渲染时烤进节点样式的数字，而 ink 的 `resized()` 只重算 yoga 布局、不重渲染 React 树，改终端尺寸后就停在旧宽高（错位、顶出多余行）。改为尺寸自己维护（`useFullscreenRows()`：首帧行数进 JSX + `prependListener` 写 yoga），底栏再固定成一行（两侧 `truncate-end` 可收缩，窄终端截断不换行）；PTY 实测 100×30→40×10→22×6 帧行数恒等于终端行数、文本仍居中，resize 后鼠标命中也照常（库的 bounds 缓存 16ms 到点自复）

- **`pnpm run tui` 跑完不退出**：入口原来只 `render(<App />)`，没等 ink 收尾。改成 `const { waitUntilExit } = render(<App />)` + `await waitUntilExit()`
- **非 TTY 直接崩溃**（`Raw mode is not supported on the current process.stdin`）：`useInput` 现在按 `isRawModeSupported` 关活。注意 ink 的判断是严格的 `options.isActive === false`，而管道下 `isRawModeSupported` 是 `undefined`，所以要写 `Boolean(isRawModeSupported)`
